# Pi ask-user 0.15.0 standalone TUI validation

**Question.** Does the released Pi v0.85.1 Bun TUI load the exact `pi-ask-user@0.15.0` extension without exposing its
bundled skill or generic model-visible tools, and is the prior Bun crash a supported-path failure?

## Finding

**Yes for configuration-level isolation; a live model call is still unverified.** The released `pi-darwin-arm64` v0.85.1
executable entered Pi's interactive TUI in a pseudo-terminal on this macOS arm64 host. Its verbose startup listed only
`npm:pi-ask-user@0.15.0` / `index.ts` under **Extensions**; with `--no-skills` it listed no **Skills** section. No
provider credentials were used.

The isolated Pi settings profile was:

```json
{
  "packages": [{
    "source": "npm:pi-ask-user@0.15.0",
    "extensions": ["index.ts"],
    "skills": []
  }]
}
```

Pi installed the exact package into the isolated `PI_CODING_AGENT_DIR`, where its manifest declares both `./index.ts`
and `./skills`. The result confirms that the explicit package filter selected the extension but excluded the extension
package's skill resource. `--no-skills` additionally prevents ambient skill discovery; it is not a substitute for the
package filter.

That earlier TUI run deliberately used this broad allow-list:

```text
--tools read,bash,edit,write,ask_user
```

It does **not** satisfy a strict no-generic-tools requirement. For that requirement, launch the same isolated profile
with:

```text
--tools ask_user --no-skills --no-context-files
```

Pi documents `--tools` as a strict allow-list applying to built-in, extension, and custom tools. Its v0.85.1 runtime
filters both built-in and extension registrations through that allow-list before they reach the model, and only
activates registered names present in it. Therefore, after the filtered package has registered `ask_user`,
`--tools ask_user` exposes that one tool and no `read`, `bash`, `edit`, `write`, or other generic tool. Do not
substitute `defaultTools: []`: Pi documents that it removes built-ins while preserving extension and SDK custom tools.
The extension source registers a tool named `ask_user`, whose UI is implemented through Pi's interactive UI APIs. A
model-visible invocation was not performed because there was no authenticated provider.

To keep **all** package resources except the extension absent, make the package selection explicit rather than relying
only on discovery switches:

```json
{
  "packages": [{
    "source": "npm:pi-ask-user@0.15.0",
    "extensions": ["index.ts"],
    "skills": [],
    "prompts": [],
    "themes": []
  }]
}
```

Pi specifies that omitted resource keys load all resources of that type and `[]` loads none. Run it with an empty,
isolated `PI_CODING_AGENT_DIR` and a neutral working directory so no ambient global or project resources can add tools
or instructions.

### Residual authority

The filter controls model-visible resources, not extension process authority. Pi extensions run in Pi's process and can
use the permissions of that process; `pi-ask-user` is third-party code with access to its installed files and Pi
extension APIs. The tool allow-list constrains the tools offered to the model, but does not sandbox extension code. The
adapter must therefore run Pi with the least filesystem/process authority appropriate to the selected workspace and
pin/review the extension package.

The exact acceptance step that remains HITL is: authenticate a test provider in a user-controlled, isolated Pi profile;
ask the model to call `ask_user`; choose an answer and separately cancel/interrupt; then verify the returned tool
result, TUI recovery, and session shutdown. The unauthenticated TUI correctly reported that no model was available
rather than proving those live-call semantics.

## Launcher conclusion

The prior `bunx --bun @earendil-works/pi-coding-agent@0.85.1 --help` exception occurs before TUI startup in the npm
CLI's bundled Undici initialisation (`webidl.util.markAsUncloneable is not a function`). Pi's npm manifest declares Node
`>=22.19.0`, while Pi separately publishes Bun-compiled standalone artifacts. Pi's v0.85.1 release workflow pins Bun
1.3.14 and builds/smoke-tests those artifacts. The supported integration target is therefore for Tomekin's Bun process
to spawn the pinned standalone Pi executable under a PTY—not to run the Node-targeted npm CLI through `bunx --bun`.
