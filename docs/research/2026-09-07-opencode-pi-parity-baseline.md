# OpenCode parity baseline for a Pi migration

**Question.** What observable OpenCode behaviour must Pi match before OpenCode can cease being a supported local
Adapter?

**Investigated:** 2026-09-07. This is a baseline of the checked-in product, not a proposal for new Pi behaviour and not
authorization to remove OpenCode. “Required” below means a Pi Adapter must preserve the outcome at its public boundary;
it need not copy the OpenCode implementation.

## Boundary of the baseline

Tomekin deliberately keeps domain behaviour portable: typed core services return `Result` values and edge adapters
translate them, rather than putting product logic in OpenCode glue
([ADR 0004](../adr/0004-typed-services-with-result-seams.md#typed-services-with-result-seams)). The present delivery
surface is nevertheless an OpenCode agent, tools, and skills
([ADR 0001](../adr/0001-opencode-first-portable-core.md#opencode-first-mvp-with-a-portable-core)). Consequently, Pi
parity includes both the deterministic service outcomes and the agent-facing procedural workflow currently held in
`.opencode`.

## Concrete retention / retirement threshold

Keep OpenCode supported until Pi has evidence for every required row:

1. deterministic parity tests cover the public tool mapping, validation/error translation, Card Query bounds/truncation,
   logging, rendering and persistence;
2. a Pi real-session run passes every applicable critical invariant in the frozen corpus, under matched reference data,
   Collection snapshot, prompt, model and reasoning effort; and
3. the team has explicitly specified and exercised Pi resume/fork/compaction/recovery behaviour, including bounded
   recovery presentation, because the present repository does not define an OpenCode equivalent to copy.

An outcome that differs only in strategic recommendation is not automatically an adapter failure. A scope leak,
deterministic illegality, fabricated live/playtest claim, padded opportunity list, persistence before confirmation,
missed final Collection recheck, altered deterministic output bound, or loss of a required persisted/rendered field is a
parity failure ([critical invariants](../testing/deck-building-workflow-scenarios.md#critical-invariants)).

## Known limitation carried into the Pi decision

The confirmed Collection allow-list lives in the working conversation rather than a structured Brief/evaluator policy
([product limitation](../product-behavior.md#deck-building-brief)). Pi must preserve that observable guardrail, but
migration is not an authorization to silently redesign it. A structured policy would be a separate product decision.
